# App Store submission

Where the app actually stands against App Store Connect's checklist, what is
already in the repository, and what is genuinely missing. The verdict on
whether the store is possible at all is in
[distribution.md](distribution.md); this file is the operational side.

## Ready in the repository

| Requirement | Where it is |
|---|---|
| App name, subtitle, promotional text, description, keywords (EN + TR) | [listing.md](listing.md) |
| Category, copyright | `LSApplicationCategoryType`, `NSHumanReadableCopyright` in `scripts/build-app.sh` |
| App icon, 16 → 1024 px and `.icns` | `app/Resources/AppIcon.*`, regenerated by `swift scripts/make-icons.swift` |
| Screenshots, 2880×1800 and 1280×800, English and Turkish | `docs/store/` — `swift scripts/make-store-shots.swift` (the raw 1120×1280 captures in `docs/images/` are **not** an accepted size) |
| Privacy manifest | `app/Resources/PrivacyInfo.xcprivacy` (no data collected, no tracking) |
| Privacy policy text | [privacy.md](privacy.md) |
| Support page | the user guide, `docs/site/` (link in the README) |
| Localizations declared | `CFBundleLocalizations = [en, tr]` |
| Minimum macOS, version, build | `LSMinimumSystemVersion 13.0`, `VERSION` file |
| Universal binary | `make dist` builds arm64 + x86_64 |

## Missing, and who can supply it

1. **An Apple Developer Program membership** (99 USD/year). Only the maintainer can buy
   it; nothing in this repository needs it until the moment of upload.
2. **A build the store would accept.** This is the real blocker, and no
   amount of paperwork fixes it — see below.

## Why today's build would be rejected

Mac App Store apps must be sandboxed, and the sandbox breaks the two things
this app does:

- `AXUIElementSetAttributeValue` — how a window's position and size are set —
  does not work inside the sandbox even with the Accessibility permission
  granted. No layouts, no placing a window on a display.
- Moving a window to another Space has no public API. `Services/SkyLight.swift`
  resolves private `SLS…` functions at runtime, which App Review guideline
  2.5.1 forbids. Resolving them through `dlsym` hides nothing and is not a
  workaround worth attempting.

So a store build is not a packaging problem; it is a different, much smaller
app. What would be left is a window *list* read through public APIs, with no
ability to move anything — not worth shipping, and not what anyone installs
this for.

## If a submittable build ever exists

The mechanics, so they are not researched twice:

1. In the developer portal: App ID `com.deskmap.app`, an **Apple
   Distribution** certificate and a **Mac Installer Distribution**
   certificate, and a Mac App Store provisioning profile.
2. Build sandboxed, with an entitlements file containing at least
   `com.apple.security.app-sandbox` and
   `com.apple.security.files.user-selected.read-write` (profile import and
   export use an open/save panel). Embed the provisioning profile at
   `Contents/embedded.provisionprofile`.
3. Sign the bundle with those entitlements, then wrap it:
   `productbuild --component Deskmap.app /Applications --sign "3rd Party Mac Developer Installer: <Name> (TEAMID)" Deskmap.pkg`
4. Upload the `.pkg` with Transporter (or `xcrun altool --upload-app`), then
   in App Store Connect create the app record, paste the metadata from
   `listing.md`, upload five screenshots per language from `docs/store/`,
   answer the privacy questionnaire with "no data collected", and submit.

Until step 2 is possible, the answer to "when does it go on the App Store"
is: it does not. The route that works today is Developer ID and a notarized
DMG, one command, described in [distribution.md](distribution.md).
